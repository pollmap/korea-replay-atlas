# 수집 완료 후 아파트 정정 재조회

## 확인한 문제와 이번 변경

기존 VPS worker는 미완료 수집과 실패 재시도만 선택했습니다. 모든 가용 작업이 complete/empty가 되면 `work_complete`로 대기했고, 별도 GitHub 수집기의 정정 예약 로직은 VPS에 연결되지 않았습니다.

이번 변경은 기존 단일 collector·bulk 잠금·장부·CAS 백업 구조를 유지하면서 **완료한 지역·월의 정정 확인을 별도 큐로 실행**합니다. 운영 활성화·실제 원천 호출·공개 지도 게시와 코드 검증은 별개입니다. 이 문서 작성 과정에서는 운영 호출·배포를 하지 않았습니다.

## 활성화와 범위

- Collector 환경변수 `KOREA_REPLAY_CORRECTION_REFRESH=1`로 켭니다. 기본값은 **0**입니다.
- 기존 priority-nine 아파트만 대상입니다. 오피스텔·범위 밖 지역·원천 제공 전 월은 재조회하지 않습니다.
- 기존 pending/partial 수집과 안전 재시도를 먼저 이어갑니다. 해당 서비스의 미완료 작업이 없으면 정정 큐를 선택합니다.
- 한 worker 주기에 최대 **50작업**, 기존 `max_requests` 이내(상한 **500요청**), **64MiB 응답**만 처리합니다. 대기 주기는 기존 300초이며 단지 개수가 아닌 지역×계약월×거래유형 단위입니다.
- 첫 활성화에서 전체 완료 장부를 pending으로 바꾸지 않습니다. 제한된 배치만 별도 큐에 등록합니다.

## 재조회 주기와 호출 한도

KST 달력과 마지막 성공 확인일 기준으로 예약합니다. 날짜가 잘못된 과거 행은 추정해 일괄 예약하지 않습니다.

| 자료 구간 | 기준 |
| --- | --- |
| 당월 포함 최근 3개월 | KST 날짜당 한 번 성공 확인 |
| 4~24개월 | 마지막 성공 확인 후 7일, 오래된 확인부터 순환 |
| 25개월 이상 | 마지막 성공 확인 후 90일, 오래된 확인부터 순환 |
| 알려진 일시 실패 | timeout/network 30분, HTTP 6시간, quota 다음 KST 날짜; 작업당 하루 최대 3회 재시도 |

매매·전월세 서비스별 일일 **8,000회** 상한은 기존 `calls` 테이블의 모든 예약을 합쳐 계산합니다. 실패·시간 초과·응답 불확실 예약도 환불하지 않습니다. 정정 호출의 70%(5,600)는 최근·4~24개월, 20%(1,600)는 과거, 10%(800)는 실패 재시도에 배정합니다. 다른 구간에 실제 대기 작업이 없을 때만 아직 사용하지 않은 할당량을 빌립니다. 모든 재배분에도 전체 8,000회 예약 검사는 매 요청 직전 같은 DB 트랜잭션 안에서 수행합니다.

예산이 이미 사용된 서비스는 다른 서비스의 작업을 막지 않습니다. API가 quota 오류를 반환하면 해당 서비스는 그 KST 날짜 동안 추가 호출하지 않으며, 다음 날짜에 재평가합니다. quota·날짜 전환은 영구 hold로 만들지 않습니다. 인증·무결성·비밀값 오류는 기존 진단/hold 경로를 유지합니다. `inconsistent_pagination` 등 안전 재시도 목록에 없는 실패는 자동으로 재시도하지 않으며 `last-run.json`의 `collection.correction.review_required`에 코드별 건수를 남깁니다. 운영자가 원인을 확인한 뒤 별도로 처리해야 합니다.

## 완료 자료와 실패 복구

`property_correction_queue`에는 선택된 작업의 새 페이지·진행 상태·기준 snapshot·실패·재시도 횟수를 저장합니다. 기존 `jobs.status`, `pages`, `snapshot`, `updated_at`은 수집 중·부분 수집·실패 시 그대로 둡니다.

- 한 지역·월의 전체 페이지가 검증되면 새 snapshot과 기존 job을 한 트랜잭션에서 교체합니다.
- 이전 원문과 snapshot 이력은 삭제하지 않습니다.
- 새 부분 페이지도 백업 감사·복원 목록과 이관 계획의 참조 검사에 포함합니다.
- 중단·재시작·CAS 복원 뒤 큐의 페이지부터 이어갑니다. 15분을 넘긴 부분 응답은 기존 Collector의 일관성 정책에 따라 새 수집을 시작하되 기존 정상 거래는 유지합니다.
- 세 번의 일시적 연속 실패는 제한 배치를 끝내고 큐의 backoff를 따릅니다. 정상 수집 전체를 영구 중지시키지 않습니다.

## 같은 원문을 다시 받은 경우

전체 페이지 수·순서·원문 SHA·크기·페이지 메타데이터가 같고 정규화 코드가 확인되면 기존 snapshot과 `jobs.updated_at`을 유지합니다. 새 확인시각은 correction queue에만 기록합니다. 원본·snapshot·변경 요약을 시각만 다르다는 이유로 다시 생성하지 않습니다.

기존 snapshot에는 정규화 코드 증명이 없으므로 처음 동일 응답 확인 시에는 **기존 원문의 원래 수집시각으로 다시 정규화해 snapshot 바이트가 재현되는지 한 번 검증**합니다. 통과하면 실제 정규화·수집·저장 코드 해시를 receipt로 보관합니다. 다음 같은 원문·같은 코드부터 그 증명을 재사용하고 코드가 바뀌면 다시 확인합니다.

정정 결과의 `changed_jobs`와 장부의 `content_revision`을 기록합니다. 동일 원문·실패·부분 페이지는 조회 DB를 다시 복사하지 않습니다. 실제 거래 교체와 revision 증가를 같은 트랜잭션에 묶고, 마지막 조회본에 반영한 revision과 대조합니다. 거래 교체 직후 게시 전에 중단돼도 다음 무변경 주기에서 빠진 조회본 게시를 이어갑니다. 양 서비스의 호출 한도 대기나 정정 opt-in을 끈 상태에서도 이미 커밋된 revision의 조회본 반영은 완료합니다. 최초 획득의 기존 게시 조건은 유지합니다.

호출을 했다는 사실과 일일 예산은 반드시 복구되어야 하므로 `calls`·큐의 작은 장부 변경은 보존합니다. 이 때문에 CAS head는 바뀔 수 있습니다. 이를 데이터 재생성과 혼동하지 않습니다. 변경 없는 원문·파생 payload 재생성은 0이지만, 호출장부 변화까지 0이라고 보고하지 않습니다.

## 반복 전체 압축 해제 방지

기존 backup_set은 매 주기 이전 CAS 전체를 해제하고 이관된 원문도 다시 해제했습니다. worker 백업에는 다음 좁은 재사용 경로를 추가했습니다.

1. CAS 객체를 한 번 정상적으로 해제·SHA 검증한 결과를 `.object-verification.sqlite`에 저장합니다.
2. 객체 SHA·원문 크기·실제 파일 장치/inode·저장 크기·mtime/ctime·검증 코드 해시가 모두 같을 때만 그 검사 결과를 재사용합니다.
3. 현재 검증 head와 닫힌 working index의 **전체 descriptor가 같은 retired 파일**만 payload 재해제를 생략합니다.
4. 새 평문·변경 파일·descriptor 불일치는 기존 바이트 검사로 보냅니다. 객체 누락·크기 변경·파일 교체·검증 코드 변경은 실패하거나 다시 해제·SHA 확인합니다.
5. 변경된 체크포인트는 기존 64KiB 조각 방식으로 저장합니다. 전체 원본 트리를 펼치거나 다시 복사하지 않습니다.

검사 캐시가 없는 **최초 실행은 기존 CAS 객체를 한 번 확인**해야 합니다. 과거 검사 수치만으로 임의 receipt를 만들지 않습니다. 이 초기 비용은 운영 활성화 전 따로 준비·측정할 수 있으며 매 주기 반복하지 않습니다. 100객체마다 검증 receipt를 커밋하고 진행 시각을 갱신하므로 중단된 초기 검사도 완료 조각을 다시 해제하지 않고 이어갑니다. 표준 수동 `backup_set()`과 복원은 캐시를 사용하지 않는 전체 SHA 검사를 유지합니다. 캐시는 읽기 속도를 위한 파생 자료이며 복구의 유일한 근거가 아닙니다. 파일 metadata가 그대로인 디스크 bit rot까지 warm cache가 발견하는 것은 아닙니다. 정기 full audit(운영 기준은 주 1회 권장)을 별도 실행해야 하며, 이 변경 자체가 해당 주간 실행을 자동 등록하지는 않습니다.

## 운영 적용 확인 순서

1. 새 API/Collector 코드와 감사 코드를 함께 배포하되 정정 env는 0으로 유지합니다.
2. 검증 캐시의 최초 생성 비용을 확인하고 기존 공개/조회 릴리스·head를 기록합니다. 수동 작업은 서비스 UID/GID 10001로 수행합니다.
3. 작은 `max_requests`로 opt-in을 켠 첫 배치에서 source_calls·선택 구간·장부 보존·부분 실패·백업을 확인합니다.
4. 같은 내용이면 원본/snapshot 수 증가가 없고, 이후 백업의 `retired_files_reused`·`retired_source_bytes_reused`가 기록되는지 확인합니다.
5. 날짜 전환·quota 대기·다음 재개를 확인한 뒤 기존 요청 상한으로 운영합니다.

꺼둘 때는 env를 0으로 바꿉니다. 큐·호출장부·이전 snapshot은 삭제하지 않습니다. 이 수집기는 공개 릴리스 포인터를 바꾸지 않으며 조회본/게시 후보 검증은 기존 절차를 사용합니다.

## 코드 검증 기록

2026-10-09 격리 fixture 기준, 저장·수집·복구·정정·VPS 전체 회귀 **556개 통과**(102.60초), 마지막 검증 receipt 재개 보강 후 관련 검사 **54개 통과**(12.63초)했습니다. 신규 재개 검사 1개를 포함합니다. compileall·git diff 검사도 통과했습니다. 독립 읽기 전용 리뷰에서 운영 차단 결함은 발견되지 않았으며, 안전 재시도 밖 오류 표시와 정기 full audit 한계를 반영했습니다. 실제 API 호출, 운영 활성화, 공개 게시 결과를 의미하지 않습니다.

후속 보강: 호출 한도 대기·정정 비활성 주기에서도 이미 커밋된 거래 revision을 조회본에 반영하는 회귀를 추가했습니다. 관련 정정·VPS·자동 원문 정리 검사 **86개 통과**(18.84초).
