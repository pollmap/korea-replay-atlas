## 이미 확보했지만 아직 게시되지 않은 자료

공개 릴리스는 현행 코드 256개, 121개월(2016-09~2026-09)의 장부를 표시하며, 실제 확인된 작업은 8,365개·원천 신고 2,108,860행입니다. 2016-09/10은 각 512개, 2016-11은 2개, 2025-06은 26개, 2025-07은 146개, 2025-08은 511개, 2025-09~2026-09는 각 512개 작업입니다. 연속 10년이나 20년 자료가 아닙니다.

최신 장부에는 이보다 307개 작업·167,477행이 추가 확보돼 있습니다. 모두 지정 9개 권역 안의 80개 현행 지역 코드에 해당합니다. 거래 합계는 검증된 snapshot에 연결된 원천 페이지 `total_count` 합계이며, 새 공개 후보의 재파싱·자산 감사는 아직 별도입니다. 취소·부적격 통계를 제외한 매매 표본 수와 동일하지 않습니다.

## 이전 게시기가 자료를 다시 숨기는 원인

재조회 준비는 이전 snapshot을 보존한 채 `jobs.status=pending`, `pages=[]`로 바꿉니다. 이전 publisher는 `complete/empty`만 노출하므로 이전 검증 snapshot 466개를 제외했습니다. 모두 2026-08이며 기존 공개 83,024행이 해당합니다. 지정 권역 안에서는 178개/55,279행입니다. 최신 장부를 그대로 게시하면 추가 307개가 있어도 완료 표시 작업이 8,365→8,206개로 오히려 감소할 수 있었습니다.

수정은 원장을 고치지 않는 게시 투영입니다. 저장 snapshot을 해시·압축 해제 검증하고, 그 안의 `audit.pages`에서 이전 원본 경로·해시·바이트·수집시각을 복구한 뒤 원본 XML을 다시 정규화해 exact JSON 일치를 확인합니다. 현재 진행 중인 새 `pages`와 섞지 않습니다. 게시 status는 마지막 검증본의 complete/empty를 유지하고 `retrieved_at`도 원래 시각을 사용합니다.

`refresh={status,error_code,attempted_at}`는 이전 자료가 있는 갱신 대기·진행·실패에만 붙입니다. 실제 재시도 호출이 없으면 attempted_at은 null입니다. `collection_coverage`는 원장의 실패·대기 집계를 별도로 유지합니다. 원본이 없는 pending/failed는 계속 미확보이며 0건으로 표시하지 않습니다.

## 안전한 후보 준비 순서

1. 원격 head를 읽기 전용으로 고정하고 검증된 체크포인트를 별도 작업 폴더에 둡니다. 원래 checkpoint를 편집하지 않습니다.
2. 이미 있는 로컬 원본·snapshot을 해시 대조 후 재사용합니다. 부족한 원격 객체만 읽기 전용으로 선택 복원합니다. 갱신 중 작업의 이전 원본 목록은 snapshot.audit.pages에서 가져옵니다.
3. `pipeline.real_estate_publish.publish(root, registry, candidate_directory)`로 후보를 만듭니다. CLI는 `--root`, `--regions`, `--output`만 받으며 기본 디스크 reserve 30GiB입니다. 함수의 명시 reserve를 조정한다면 실제 여유와 예상 산출량을 먼저 확인합니다. 검사를 없애거나 public/dist에 직접 출력하지 않습니다.
4. 기본 24MiB 파일 한도·4MiB 목표 청크·18,000파일 상한, 원문 해시·재파싱, 임시 폴더의 원자적 후보 완료를 유지합니다. 중간 실패는 공개 pointer를 바꾸지 않습니다.
5. 새 307개와 유지 466개의 ID·원천 행수·원래 수집시각을 비교하고, 같은 새 release에 단지 좌표·기본정보·탐색 색인을 재생성합니다. 구 release 문자열만 바꾸어 재사용하지 않습니다.
6. 후보 자산·TS 계약·대표 단지 이력·공유 복원을 통과한 뒤에만 별도 배포 절차로 전달합니다. private 원본은 공개하지 않습니다.

이번 변경은 수집과 공개 사이의 자료 누락을 해결하는 단계입니다. 전체 20년 수집 완료, 미확보 과거 데이터 생성, 원격 공개 자동 게시 완료와 구분합니다.
