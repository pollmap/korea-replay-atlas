# GPU 배치 처리와 카메라 정지 판정 — 2026-09-17

이 기록은 Radeon 860M에서 실행한 프로덕션 빌드 검증입니다. 전국 데이터 릴리스 `pub-a55c6a081e5782db`는 그대로 사용합니다. 수정본 `363089fb-7b4b-4db4-9e39-52f7084c8ba9`를 [공개 지도](https://korea-replay.legacy.example.invalid/)에 100% 반영했으며 미리보기·공개 HTTP 검사가 각각 67건 통과했습니다. 성능의 완료 범위는 아래 측정 조건으로 제한합니다.

## 해결한 문제

### 이동이 끝났는데 상세 자료가 나오지 않음

기존 공개 버전 `58cd8d4b-5979-47cd-8742-542ffdbd996d`에서 울릉도→독도 이동 후 2분 이상 `cameraMoving=true`가 유지됐습니다. 독도에 도착했지만 울릉도 자료 13개가 남고 새 지역 목록이 적용되지 않았습니다. 네트워크 실패는 없었습니다.

같은 기존 종료 판정을 쓰는 계측 빌드에서 38.051초 간격으로 읽은 카메라 경도·위도·높이는 완전히 같았습니다. 방향의 roll 값만 약 6.4×10⁻¹³ rad 달랐고 여전히 이동 중이었습니다. 설치된 Cesium 1.145는 방향·위치·frustum을 `EPSILON15`로 비교한 뒤 정지 이벤트를 냅니다. 실제 Camera/View를 쓰는 별도 재현에서도 비행 후 1μm 위치 잡음만으로 종료 이벤트가 120초간 나오지 않았습니다. 이 재현은 취약한 종료 조건을 증명하며, 공개 환경에서 그 잡음을 처음 만든 내부 원인까지 확정하는 것은 아닙니다.

`src/camera-settle.ts`의 위치·방향 관찰로 종료를 판정합니다. 위치 1cm·방향 벡터 1e-8의 허용 오차를 쓰고 마지막 의미 있는 위치를 기준으로 비교해 느린 누적 이동도 감지합니다. 350ms 조용한 구간 뒤 새 유효 표본을 확인해야 상세도를 복원합니다. 백그라운드에서 타이머만 지났다고 비행이 끝났다고 판정하지 않습니다. 화질 조절로 생기는 내부 픽셀 반올림이 이동을 다시 시작하지 않도록 CSS 화면 비율을 사용합니다.

수정 빌드의 같은 울릉도→독도 경로에서는 이동·상세 대기 상태가 모두 false로 끝났고 독도 자료 6개, 피처 653개·정점 100,011개로 교체됐습니다. 그림자·정지 지형 상세도도 복원됐습니다. 이전 위치·방향·원본 지도 좌표를 임의 보정하지 않았습니다.

증빙: `.local/rendering-20260917/dokdo-public-after-return.json`, `dokdo-old-motion-a.json`, `dokdo-old-motion-b.json`, `dokdo-fixed.json`. 초기 `dokdo-public-ready.json`이라는 파일명은 완료 판정이 아니며, 그 안의 실제 상태는 이동 고착입니다.

### GPU 준비 작업이 한꺼번에 시작됨

원래 Primitive 컬렉션은 전체 자료를 만든 뒤 장면에 붙었습니다. 새 경로는 첫 배치부터 장면에 붙이고 다음 배치 전에 프레임을 양보합니다. 배치 한도 128개·8,192정점, 원본 좌표·ID·선택 속성은 유지합니다. 점·라벨 컬렉션은 구성 중 반복 GPU 재생성을 피하도록 완료 시 표시합니다.

취소 시 프레임이 멈춘 탭에서도 해당 작업의 대기를 즉시 해제해 선택 정보·중간 Primitive를 정리합니다. 다른 작업이 공유하는 프레임 예약은 취소하지 않습니다. 성공한 중간 컬렉션은 다시 추가하거나 파괴하지 않고 완성 자료로 인계합니다.

자동 화질의 MSAA는 정밀 4·균형 2·경량 1로 조절합니다. FXAA는 유지합니다. MSAA를 이동할 때마다 켰다 끄지 않아 framebuffer를 반복 생성하지 않습니다. 이는 윤곽선 처리의 품질·부하 조절이며 건물 형상이나 원천 높이의 변경이 아닙니다.

### 작은 화면에서 검색 결과 첫 줄이 눌리지 않음

실제 작은 브라우저 창에서 검색 결과 첫 줄의 중앙을 누르면 뒤의 `햇빛 실험` 버튼이 눌렸습니다. 검색 결과가 속한 헤더의 쌓임 순서 3보다 모바일 메뉴 4가 높았습니다. 화면 너비 780px 이하에서 헤더를 6으로 올려 검색 결과를 메뉴·열린 레이어 패널 위에 표시합니다. 알림 7·출처 모달 10의 순서는 유지합니다. 검색·좌표·렌더 로직의 변경은 없습니다.

`mobile-search-overlap-before.json`은 실제 클릭 중심의 대상이 검색 결과가 아닌 `햇빛 실험`임을 기록합니다. 최초 미리보기의 `preview-dokdo.json`은 이 메뉴 겹침으로 이동 자체가 시작되지 않은 결과입니다. 넓은 화면에서 같은 미리보기의 이동이 정상 종료된 기록은 `preview-dokdo-wide.json`이며, 앞선 카메라 정지 고착과 이 UI 문제를 혼동하지 않습니다.

수정 후 같은 실제 창에서 클릭 중심이 `독도 경북 울릉군` 결과로 바뀌었고, 클릭 뒤 독도 자료 6개·이동 false·상세 대기 false·남은 작업 0으로 끝났습니다. `햇빛 실험` 모드도 유지됐습니다. 증빙은 `mobile-search-overlap-after.json`, `mobile-search-selection.json`입니다. 별도로 CSS 구문과 너비 390·581·780·781·1280px의 쌓임 순서를 검사했습니다.

## 남은 초기 로딩 병목

중간 빌드의 38.75초 CPU 프로파일에서 geometry 준비는 여러 프레임에 분산됐습니다. GroundPolyline 업데이트는 시작 후 1.74~11.73초, 정점 배열 생성은 6.65~11.56초에 나타났습니다. 실제 렌더 작업은 처음 11.76초 안에 집중됐으므로 이 전체 기록 시간을 로딩 시간이나 정지 FPS로 해석하지 않습니다.

큰 초기 스파이크에는 라벨 글자·atlas 생성이 남았습니다. 가장 긴 연속 렌더 표본 구간 105.4ms 중 LabelCollection 업데이트가 81.6ms였습니다. 전체 GC 표본은 300ms, 가장 긴 연속 구간은 21.266ms였습니다. 작업별 최대치의 시각이 없어 21.8ms line-instance와 같은 사건이라고 단정할 수 없습니다. 특정 라벨 컬렉션의 ID도 이 프로파일에는 없습니다.

**전국 일반 탐색 P95 33ms·모든 분할 생성 8ms 목표의 전면 통과는 아닙니다.** 초기 글자·shader 준비와 간헐적인 긴 생성 구간을 더 줄여야 합니다. 파일 전송 시간 개선 기록은 [PERFORMANCE_LOADING.md](PERFORMANCE_LOADING.md)에 별도로 있습니다.

이후 적용한 공통 라벨 대기열·세대별 자원 해제와 2026-09-19의 동일 화면 비교는 [라벨 렌더링 성능 기록](LABEL_RENDERING_PERFORMANCE.md)에 있습니다. 그 후보의 검증·배포 상태는 이 문서의 기존 e86 공개 기록과 구분합니다.
