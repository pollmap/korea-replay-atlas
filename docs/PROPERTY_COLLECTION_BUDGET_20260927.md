# 자동 수집 처리량·무료 예산 감사 — 2026-09-27

## 결론

현재 자동 수집은 실제로 켜져 있다. 읽기 전용 확인 당시 GitHub 변수는
`PROPERTY_COLLECTION_ENABLED=true`, 25회/16 MiB였고 cron은 하루 6회였다.
이 문서는 설정을 변경하거나 수집을 추가 실행한 기록이 아니다.

먼저 과거 최초 확보와 최근 정정 대기를 분리해야 한다. 수정 후 **100회/64 MiB
대표 실행의 작업 완료 수·실행 시간·D1 사용량을 측정하고, 150~200회까지 단계적으로
판단**하는 것을 추천한다. 1,000회/512 MiB는 이번 변경에서 채택하지 않는다.
100회 설정도 우선지역 10년 확보를 즉시 완료시키는 방안은 아니다.

없는 작업만 선택하고, 안전 재시도와 pagination 사전 검사에도 같은 조건을 적용한다.
recent/history는 기존 갱신 책임을 유지한다. 원본이나 이전 snapshot을 삭제하지 않는다.

## 완료 기간의 조건부 계산

처음 세 번의 유효한 최초 확보 backfill은 각각 18회→15작업, 19회→14작업,
25회→23작업을 완료했다. 관측 효율은 **52작업/62호출 ≈ 0.839**다. 오류, 여러 페이지,
지역별 거래량과 정정 상태에 따라 달라지는 작은 표본이며 미래 보장치가 아니다.

자동 순환은 4회 중 3회가 backfill이다. 하루 6회가 모두 실행되면 평균 4.5회/일을
최초 확보에 쓸 수 있다. GitHub 실행 지연·실패, 매달 새 작업과 재시도는 아래에서 제외했다.

| 가정 | 최초 확보 작업/일 | 서울·인천 7,408개 | 우선지역 24,838개 | 전국 53,535개 |
|---|---:|---:|---:|---:|
| 현재 25회 상한, 1호출=1작업이라는 낙관적 하한 | 최대 112.5 | 최소 66일 | 최소 221일 | 최소 476일 |
| 현재 실측 17.33작업/backfill을 유지 | 약 78 | 약 95일 | 약 318일 | 약 686일 |
| 100회가 모두 실행되고 관측 효율 유지 | 약 377 | 약 20일 | 약 66일 | 약 142일 |
| 150회가 모두 실행되고 관측 효율 유지 | 약 566 | 약 14일 | 약 44일 | 약 95일 |
| 200회가 모두 실행되고 관측 효율 유지 | 약 755 | 약 10일 | 약 33일 | 약 71일 |

마지막 두 행은 64 MiB 안에 해당 요청 수가 들어가는 경우만 성립한다. Collector는
다음 응답 최대 8 MiB 여유를 보존한다. 따라서 마지막 응답을 포함한 실제 종료점은
응답 크기에 따라 달라진다. 최근 관측한 평균 0.216~0.473 MB/응답을 그대로 적용하면
64 MiB의 56 MiB 예약 전 여유로 약 124~272회가 가능하다. 100회는 이 표본에서
요청 상한이 먼저 걸릴 가능성이 높고, 150~200회는 큰 페이지 지역에서 바이트 제한이
먼저 걸린다. 200회를 설정했다고 200회 실행 또는 33일 완료라고 보고하면 안 된다.

## 공식 원천 호출 조건

[아파트 매매 상세](https://www.data.go.kr/data/15126468/openapi.do)와
[아파트 전월세](https://www.data.go.kr/data/15126474/openapi.do)는 2026-09-27 재확인 당시
무료·개발계정 신청 가능 트래픽 10,000을 안내한다. 포털의 22번 오류 설명은 일일 호출
허용량 초과, 23번은 초당 허용량 초과다. 기존 저장 근거는 `PROPERTY_PIPELINE.md:14`다.
이는 **사용자 계정의 현재 승인서에 명시된 개별 할당을 새로 열어 확인한 것과 다르다.**
승인된 키로 실제 응답이 수집된 사실은 확인되지만 계정별 트래픽 증가 승인 증거는 없다.

기존 자체 상한은 서비스별 KST 일간 8,000회다. 100~200회 × 하루 6회는 두 API 합계
최대 600~1,200회이며 한 API에 몰려도 공개 기본 트래픽보다 작다. 다른 프로그램의
같은 키 사용은 별도로 고려해야 한다. source 변경·키 교체·병렬 수집을 통해 한도를
우회하지 않는다. 우선 검증된 아파트 매매·전월세로 진행하고, 오피스텔·단지 속성 수집을
이 이력 backfill의 예산에 섞지 않는 편이 완료 기간과 이용 상태를 명확히 한다.

## D1·Worker·실행 시간 병목

최신 25회 실행은 7분 17초 걸렸다. 실행을 포함하는 05:25~05:35 UTC의 계정 analytics는
읽기 26,728행, 쓰기 782행, SQL readQueries 802 + writeQueries 529였다. 계정 전체
시간창이므로 다른 작업과 집계 지연이 포함될 수 있으며 정확한 이 실행 단독 계량치는 아니다.

현재 broker는 SQL 하나당 HTTP Worker 요청 하나를 보낸다. 이 작은 실행의 관측 비율은
원천 1회당 약 53개 SQL이다. 초기 manifest/checkpoint 복원 등 고정 비용도 포함하므로
대규모 실행에 그대로 비례하지 않는다. 아래는 검증을 대체하는 예측이 아니라 **확대 전
용량 검사의 참고값**이다.

| source 예산/일 | 같은 비율의 Worker 요청 | 같은 비율의 D1 쓰기 |
|---|---:|---:|
| 100 × 6 = 600 | 약 31,944 | 약 18,768 |
| 200 × 6 = 1,200 | 약 63,888 | 약 37,536 |
| 미채택 1,000 × 6 = 6,000 | 약 319,440 | 약 187,680 |

Workers Free 요청 100,000/일과 D1 읽기 500만·쓰기 10만행/일은 계정의 다른 서비스와
공유된다. 감사 시점 당일 D1은 읽기 1,549,881행·쓰기 13,205행이었다. 한도 초과 시
오류가 나는 Free 구성을 유지하며 유료 전환을 하지 않는다. source 한도만 맞춰도 이
저장 계층 한도는 초과할 수 있다. [Workers 한도](https://developers.cloudflare.com/workers/platform/limits/),
[D1 가격·초기화 기준](https://developers.cloudflare.com/d1/platform/pricing/).

현재 자동화 하드 상한은 500회/64 MiB이고 Collector도 64 MiB를 넘는 실행을 거부한다.
1,000/512는 변수 변경만으로 실행되지 않는다. workflow에는 120분 timeout이 있고,
0.3초 최소 간격 외에 원천 응답·원본 readback·정규화·checkpoint 게시 시간이 붙는다.
단순하게 7분 17초/25를 1,000회로 늘리면 약 291분이며 고정 비용을 제외해도 120분
완료는 검증되지 않았다. timeout이나 중간 저장 실패는 owner를 자동 해제하지 않는다.
따라서 반복 중단으로 운영이 멈추지 않게 100회 대표 실행부터 계량해야 한다.

후속 최적화는 고정 복원 비용과 원천 1회당 가변 SQL을 분리 계량하고, 이미 이번
실행에서 해시 readback을 마친 원본의 중복 확인, 여러 짧은 읽기의 안전한 batch 등을
검토하는 것이다. CAS·reservation 원자성·원본 해시 검증은 유지해야 한다. 이번 패치에서
archive/broker를 다시 작성하거나 batch/응답 크기 한도를 바꾸지 않는다.

## 저장량·보존·GitHub 무료 조건

현재 원본 object shard 4개는 각각 172,163,072 / 132,571,136 / 165,122,048 /
135,491,584 B다. 합계 605,347,840 B이며 shard별 자체 380 MiB cap까지 합계 여유는
988,487,680 B다. 해시 분배가 같지 않아 특정 shard가 먼저 멈출 수 있다. 모든 원본과
이전 snapshot/head를 보존하므로 다운로드 예산 확대는 원격 저장 증가도 가속한다.
현재 여유로 우선지역·전국 10년 원본이 모두 들어간다는 검증은 없다. 대표 실행에서
신규 완료 작업당 원격 저장 증가량을 함께 계량해야 한다. 자료를 임의 삭제하지 않는다.

확인한 저장소는 public, runner는 기본 `ubuntu-24.04`이며 무료 표준 runner 조건에
해당한다. 공식 사양은 4 vCPU·16 GB RAM·14 GB SSD이고 job 종료 후 로컬 workspace는
영구 백업이 아니다. 현재 수집 workflow에는 artifact/cache 업로드가 없고 실제 최신
실행 artifacts API 결과도 0개였다. 원본과 checkpoint는 private D1에만 남긴다.
[공식 runner 사양](https://docs.github.com/en/actions/reference/runners/github-hosted-runners).

공개 표준 runner 실행 시간은 무료다. Larger runner는 공개 저장소에서도 유료이므로
사용하지 않는다. artifact/cache 저장량은 실행 시간과 다른 과금 항목이며 raw를
GitHub artifact로 올리는 우회 저장안을 채택하지 않는다. 로그는 artifact 저장량에
산입되지 않는다. [GitHub Actions 요금](https://docs.github.com/en/billing/concepts/product-billing/github-actions).

artifact/log는 기본 보존기간과 조직·저장소별 설정이 있으며 공개 저장소의 보존 설정은
영구 원본 보존을 보장하지 않는다. 현재 저장소의 개별 보존일을 새로 확정하지 않았고,
원본 artifact 자체가 없으므로 보존기간 확대도 수행하지 않았다.
[공식 보존 설정](https://docs.github.com/en/organizations/managing-organization-settings/configuring-the-retention-period-for-github-actions-artifacts-and-logs-in-your-organization).

## 다음 검증 순서

1. 최초 확보/갱신 분리 회귀 → 코드 리뷰·CI → merge.
2. root가 100회/64 MiB의 대표 수동 실행을 결정한다. 이 감사에서는 추가 수집하지 않았다.
3. first-acquisition 증가량, 실제 source bytes/횟수, 총 실행 시간, broker 요청,
   D1 rows-read/written, 각 shard 크기 증가, 새 head/owner 해제를 대조한다.
