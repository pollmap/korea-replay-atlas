# 비공개 원본 보관 객체 압축

2026-09-28. 이 변경은 서버 수집기의 비공개 D1 복구 저장소에 적용한다. 정규화 JSON snapshot의 XZ와 별개이며 공개 거래 게시, 앱·지도·3D의 변경이 아니다. 20년 확보·전체 무료 보관 완료를 뜻하지 않는다.

## 저장과 복원 계약

외부 descriptor의 `sha256`·`bytes`는 계속 **압축 전 원본**을 식별한다. 기존 zlib 객체는 원래 키와 모든 조각을 보존하고, 바이트 검증에 성공하면 압축을 다시 하지 않고 그대로 재사용한다. 기존 JSON/gzip/XZ snapshot 파일, manifest 1·2와 분할 체크포인트 계약도 유지한다.

새 객체는 zlib6과 XZ preset3를 비교해 **형식 헤더까지 포함한 XZ가 더 작을 때만** XZ를 선택한다. 작은 객체나 절감 효과가 없는 객체는 기존 zlib 방식이다. 따라서 Base64와 조각당 예산을 포함한 기존 zlib 최악 비용 사전검사보다 저장 비용이 늘어나지 않는다. 이는 payload 계산의 보장이지 SQLite 페이지·파생물·향후 이력의 총 용량 보장이 아니다.

새 XZ의 저장 키는 `SHA256("korea-replay:archive:xz3-v1:" + 원본 SHA의 ASCII)`이다. 기존 원본 SHA 키와 격리하므로 zlib만 아는 이전 작성기가 새 형식의 조각에 쓰지 않는다. 새 읽기 경로는 기존 키를 먼저 확인하고, 없거나 검증에 실패하면 새 키의 완전한 객체를 검증한다. 한쪽의 불완전한 조각이 다른 쪽의 검증 완료 사본을 가리지 않는다. 어느 쪽도 검증되지 않으면 오류로 중단한다. 같은 원본을 다른 형식으로 자동 이전하거나 기존 객체를 삭제하지 않는다.

XZ 객체의 조각 결합 결과는 아래 순서다.

| 바이트 | 의미 |
|---|---|
| `KRAR` + `0x01` + `XZ3` + `0x00` | 형식 버전·codec, 9바이트 |
| 32바이트 | 압축 스트림 SHA256의 바이너리 표현 |
| 나머지 | FORMAT_XZ·CRC64·preset3 단일 스트림 |

부분 업로드를 재개할 때 첫 조각의 형식을 유지한다. 존재하는 모든 조각과 현재 인코더의 결과가 일치해야 빠진 조각만 추가한다. 첫 조각이 없거나 충돌하면 덮어쓰지 않고 중단한다. 새 업로드도 첫 조각을 `INSERT OR IGNORE`로 확보하고 읽어 검증한 다음 나머지를 쓴다. 첫 조각의 전체 스트림 SHA는 다른 인코더 출력이 섞이는 것을 막는다. 완전한 기존 객체는 원본 SHA가 맞으면 인코더 버전과 무관하게 재사용한다.

읽기는 조각 순서·개수·Base64 크기, 압축 스트림 SHA, 해제 바이트 수·원본 SHA를 검사한다. XZ 사전 메모리는 64MiB로 제한하며, 해제 출력은 descriptor 크기+1에서 멈춰 폭증을 거부한다. EOF·CRC64·남는 바이트·복수 스트림·미지원 버전 오류도 거부한다. 메모리 제한은 압축 해제기의 사전 예산이며 전체 Python 프로세스 RSS 한도와 같지 않다. [Python 공식 계약](https://docs.python.org/3/library/lzma.html), [XZ 공식 설정](https://tukaani.org/xz/man/xz.1.html).

## 실제 원본 표본

이전 조사와 동일한 검증 원본 XML 64개, 총 13,245,614바이트를 사용했다. 매매·전월세 각 32개이며 2016·2025·2026년에 편중되어 20년 전체를 대표하지 않는다. 원본 SHA·크기를 확인하고 새 실제 인코더, 이전 decoder, 정확한 D1 SQL을 사용하는 로컬 저장·복원 검사를 수행했다.

| Base64 payload | 바이트 |
|---|---:|
| 기존 zlib6 | 1,092,120 |
| 새 적응형 저장(헤더 포함) | 687,000 |
| 표본 절감 | **37.09%** |

55개는 XZ, 9개는 zlib를 선택했다. 이는 원본 표본의 payload 실측이며 원격 D1 물리 용량·모든 연도·브라우저 속도·전체 저장 여유로 확대하지 않는다. 기존 4개 shard의 내부 한도, 호출 100회·64MiB 한도와 원본 보존 원칙은 바꾸지 않는다.

## 운영 검증과 복구

관련 회귀는 legacy·신규 혼합 백업 복원, 원본 바이트와 과거 head 보존, 페이지 경계를 넘는 조각, 업로드 중단·경쟁·형식 충돌, 해제 출력·메모리·SHA·CRC·trailing-data 검사다. 독립 검토에서 재현한 'legacy 부분 업로드가 완전한 XZ를 가리는 경우'도 복원·재사용 회귀에 추가했다. Broker의 기존 SQL 허용 목록과 요청·응답 제한 안에서 동작하며 DB 스키마·Worker 변경은 없다. 공개 CI 이후 병합된 코드로 한 번의 제한된 수집을 수행해 원격 신규 객체의 형식·조각·해제 원문과 head·기존 장부 보존을 따로 확인한다. 이 문서의 로컬 표본 결과만으로 원격 적용 완료라고 판단하지 않는다.

기존 `size_after` 기반 shard 검사와 수집 lease는 유지한다. 압축 개선을 계정의 모든 동시 작성기를 포괄하는 원자적 공간 예약으로 표현하지 않는다.

**새 객체가 저장된 이후에는 이 codec을 읽을 수 있는 수집·복원 코드를 사용해야 한다.** zlib만 지원하는 과거 코드로 수집기를 되돌리면 새 객체를 찾지 못해 중단된다. 앱의 과거 Pages 버전 복원과는 별개다. 장애 시 archive head나 원본을 삭제·역행시키지 말고, 기존 파일을 보존한 채 새 decoder가 포함된 수정본으로 복원·읽기 검증부터 수행한다. 불확실한 원격 쓰기나 수집 dispatch를 자동 반복하지 않는다.
