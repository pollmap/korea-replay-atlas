# 실거래 수집기의 원격 보존과 자동 운영 연결

## 목적과 완료 경계

`pipeline.real_estate_archive`는 공공 API 수집 장부와 원본을 **비공개 Cloudflare D1**에 보존하고 새 폴더로 복구합니다. 웹사이트 데이터 게시기나 자동 수집 스케줄러가 아닙니다. 원격 복구가 검증되지 않은 상태에서 로컬 원본을 삭제하거나 자동 수집을 켜지 않습니다.

자동 운영은 원격 복구 → 호출 예산 예약 → 제한된 수집 → 원본·장부 확정 → 자료 감사 → 불변 게시 순서로 연결합니다. 이 모듈은 그중 원격 복구와 보존을 구현합니다. 키가 포함된 인증 파일, 브라우저 상태, 게시 후보, 내부 로그는 백업 대상에서 제외합니다.

## 저장 계약

- 제어 DB 1개와 객체 DB 4개를 사용합니다. 기존 서비스 DB를 재사용하지 않습니다. 객체 SHA-256의 첫 바이트를 4로 나눈 나머지로 저장 위치를 정합니다. **배열 순서와 DB ID를 바꾸면 기존 객체를 찾을 수 없습니다.**
- SQLite online backup으로 일관된 장부를 복사하고 무결성·현재 참조·과거 스냅샷 파일의 해시를 검사합니다. 진행 중인 collector lease가 있으면 거부합니다.
- `checkpoint.sqlite`, `raw`, `snapshots`, `registry`, `runs`, `changes`, `history-windows`만 허용합니다. 내용 주소 파일명, 경로 탈출, 심볼릭 링크·junction, 최대 파일 수·크기를 검증합니다.
- 파일을 원본 상태로 묶어 zlib로 무손실 압축한 뒤 48KiB 조각을 저장합니다. 복구 시 압축 해제 상한, 객체 SHA, 각 파일 SHA를 모두 검사합니다. 재수집·원본 변경·공개 게시를 수행하지 않습니다.
- 작은 SQL 묶음과 제한된 조회 페이지를 사용합니다. **새 버전 등록 전에 모든 객체를 원격에서 다시 읽어 검증**합니다. 네트워크 실패·중간 종료는 새 정상본으로 등록되지 않습니다. 부분 객체는 같은 내용으로 재개할 수 있습니다.
- 기존 정상본의 파일이 로컬에서 누락되면 증분 백업을 거부합니다. 새 파일 때문에 과거 전체를 다시 묶지 않고 기존 객체 주소를 유지합니다.
- 마지막 정상본 포인터는 이전 SHA·크기가 같은 경우에만 갱신합니다. 다른 백업이 먼저 끝났으면 오래된 작업의 갱신을 거부합니다. 이 비교는 **백업 포인터 보호**이며 수집 호출의 분산 잠금이 아닙니다.
- 객체 DB당 380MiB에서 추가 쓰기를 중지합니다. 삭제·유료 전환·R2 활성화는 하지 않습니다. 장기 정정본 축적은 유한한 무료 용량을 사용하므로 잔여 용량을 운영 지표로 관리해야 합니다.

[D1 공식 한도](https://developers.cloudflare.com/d1/platform/limits/)에 따르면 Free는 DB당 500MB, 계정 전체 5GB, 최대 10개 DB이며 [무료 일일 한도](https://developers.cloudflare.com/d1/platform/pricing/)도 공유됩니다. 다른 서비스의 사용량을 포함한 계정 한도는 별도로 확인해야 합니다. 모듈의 자체 중지 기준은 무료 요금제 확인을 대체하지 않습니다.

## 실행과 복구

Python 표준 라이브러리만 사용합니다. 인증정보는 `CLOUDFLARE_API_TOKEN` 환경변수로 전달하며 명령행 인자·Git·출력에 넣지 않습니다. 설정 JSON은 아래 구조이고 토큰은 포함하지 않습니다.

```json
{
  "account_id": "ACCOUNT_ID",
  "control_database": "CONTROL_DATABASE_UUID",
  "object_databases": ["OBJECTS_0_UUID", "OBJECTS_1_UUID", "OBJECTS_2_UUID", "OBJECTS_3_UUID"]
}
```

```text
python -B -m pipeline.real_estate_archive initialize --config PRIVATE_CONFIG_PATH
python -B -m pipeline.real_estate_archive backup --config PRIVATE_CONFIG_PATH --root PRIVATE_COLLECTOR_ROOT
python -B -m pipeline.real_estate_archive status --config PRIVATE_CONFIG_PATH
python -B -m pipeline.real_estate_archive restore --config PRIVATE_CONFIG_PATH --root NEW_RESTORE_DIRECTORY
```

복원 대상은 존재하지 않는 새 디렉터리여야 합니다. 실패한 복원 폴더는 자동으로 지우지 않으며, 다음 시도에는 다른 새 디렉터리를 사용합니다. 원격 버전의 전체 파일을 복구한 뒤 SQLite 무결성·작업 상태별 수·호출 수·스냅샷 수·참조 해시를 다시 검사합니다. 복원 중간 결과는 수집기나 게시기에 연결하지 않습니다.

로컬 장비를 잃었으면 Cloudflare 계정에서 프로젝트 이름의 control, objects-0~3 DB를 확인해 같은 순서로 설정을 복원할 수 있습니다. 저장소 이름은 `korea-replay-property-control`, `korea-replay-property-objects-0`~`3`입니다. 공개 HTTP 조회 경로를 만들지 않았으며 읽기에도 Cloudflare 인증이 필요합니다.

## 새 달 추가

`real_estate_fetch --advance-window --months 121`은 현재월이 앞으로 진행할 때 새 작업을 추가하고, 이전 모든 월·원본·스냅샷·호출 기록을 유지합니다. 최근 완료월을 우선하도록 작업 우선순위만 조정합니다. 121개월에서 다음 달로 넘어가면 122개월이 되며 오래된 월을 삭제하지 않습니다. 시간을 뒤로 돌리거나 현재 조회 기간과 이전 최신월이 겹치지 않는 큰 도약은 거부합니다. 동일 명령 재실행은 작업을 중복 생성하지 않습니다.

이 옵션은 이미 완료된 최근월의 정정 재조회 정책을 대신하지 않습니다. 자동 수집을 연결할 때 최근월 재조회와 과거월 순환 검사를 별도 일정으로 정해야 합니다.

## 원격 실행 소유권과 호출 예약

`pipeline.real_estate_run_guard.CollectionGuard`와 `guarded_transport`는 기존 `Collector`에 연결할 수 있는 원격 실행 보호 장치입니다. 설치·업그레이드 시 archive의 `initialize()`와 guard의 `initialize()`를 모두 호출합니다. 아직 GitHub 정기 실행은 연결하지 않았습니다.

- 원격 정상 백업의 SHA·크기가 일치할 때 하나의 실행기만 소유권을 얻습니다. 실행 세대 번호를 증가시켜 이전 실행기의 갱신을 거부합니다. 15분 기한을 넘긴 실행은 자동 인계하지 않으며 복구 검토가 필요합니다.
- 한국 시간 날짜와 매매·전월세 서비스별로 호출 전에 원격 예약을 만듭니다. SQLite trigger가 예약과 사용량 증가를 하나의 원자적 작업으로 처리하고, 서비스별 하루 8,000회를 초과하면 거부합니다. 이 guard를 거치지 않는 다른 프로그램의 호출은 집계하지 못합니다.
- 재사용한 예약 ID는 호출을 다시 허용하지 않습니다. 실패·타임아웃·중단된 예약도 사용량에서 차감하지 않습니다. 알 수 없는 응답을 성공이나 0건으로 바꾸지 않습니다.
- 정상 API 본문은 비밀키 반사 검사를 통과한 뒤 D1에 쓰고 다시 읽어 확인한 다음에만 로컬 수집기에 전달됩니다. 원격 기록 실패는 `remote_checkpoint_error`로 즉시 수집을 중단합니다.
- 소유권을 얻은 실행기가 있는 동안 수동 백업도 정상본 포인터를 덮어쓸 수 없습니다. 실행기는 미처리 예약이 없고 새 정상 백업이 등록된 뒤에만 잠금을 해제합니다. API를 전혀 호출하지 않은 점검 실행은 같은 백업으로 해제할 수 있습니다.
- 원격 예약에 저장한 원본도 비공개 객체입니다. 웹사이트 공개 데이터와는 별도로 보존하며, 전체 장부 확정·재시작 복구·자료 게시의 검증을 대체하지 않습니다.

D1 REST의 trigger 분리기는 괄호 없는 `CASE ... END`를 잘못 처리할 수 있어 괄호를 사용합니다. [Cloudflare 저장소의 해당 재현 사례](https://github.com/cloudflare/workers-sdk/issues/4727)와 동일한 실패를 실제 D1에서 확인했고, 수정 후 설치·동시 소유권 거부·잘못된 소유권의 예약 거부·갱신·해제가 통과했습니다. 이 원격 검증의 공식 API 호출 수는 0입니다.

## 남은 자동 운영 관문

1. 자동 실행용 최소 권한 인증과 GitHub 실행 환경 연결. 로컬에서 원격 guard를 적용한 실제 공식 API 호출·저장·복원은 아래와 같이 검증했지만, 정기 실행은 아직 활성화하지 않았습니다.
2. 중단된 실행의 원격 예약·저장 원본과 마지막 정상 장부를 대조하는 복구 절차. 단순 잠금 삭제나 호출 수 초기화는 복구로 취급하지 않습니다.
3. 부분 복원 실행기의 무료 GitHub 실행 환경 측정 및 저장 공간 증설 계획. 현재 4개 객체 DB의 내부 용량 제한에 도달하기 전에 확장해야 하며, 기존 해시 배치 순서를 임의로 바꾸면 과거 객체를 찾을 수 없습니다.
4. 새 달 추가·최근 정정·과거 순환 갱신과 과거 유효 지역 코드 대응표.
5. 후보 데이터 감사 및 앱/데이터 릴리스의 원자적 공개·롤백.

이 관문이 남아 있는 동안 GitHub의 `property-plan.yml`은 계속 계획만 생성합니다. 노트북 없이 게시된 웹사이트를 이용하는 것과 자료가 자동으로 새로 수집되는 것은 각각 별도 상태입니다.

## 필요한 자료만 복원하는 실행기

`pipeline.real_estate_remote`는 원격 정상 manifest를 고정한 뒤 장부와 지역 코드 원본만 먼저 복원합니다. 진행 중이던 작업의 이전 원본 페이지·스냅샷은 해당 작업에서 필요할 때 가져옵니다. 이미 보존된 파일 참조는 모두 유지하고, 새 원본·정규화 결과·장부만 검증해 새 manifest로 확정합니다. 새 파일은 다시 읽어 해시를 확인하고, 이전 파일은 검증된 불변 manifest에 대한 참조 일치 여부를 검사합니다. 이를 전체 원본의 매번 재검증이라고 표현하지 않습니다.

```text
python -B -m pipeline.real_estate_remote --config PRIVATE_CONFIG_PATH --root NEW_RUN_DIRECTORY --secret-file PRIVATE_KEY_JSON --max-requests 25 --collect-month 201611 --execute
```

- `CLOUDFLARE_API_TOKEN`은 환경변수, 공식 서비스키는 `DATA_GO_KR_SERVICE_KEY` 환경변수 또는 비공개 JSON의 같은 키로 전달합니다. 토큰·서비스키·실제 계정 설정을 저장소에 넣지 않습니다.
- 최초 실행은 **검증된 원격 장부**의 날짜·서비스별 기존 호출 기록을 D1 예산에 이관합니다. 이관이 완료되기 전에는 새 예약을 거부합니다. 중간 이관은 같은 입력으로 재개하며, 이후 실행에서는 다시 합산하지 않습니다.
- 매번 존재하지 않는 새 실행 디렉터리를 사용합니다. 기존 원본·실행 디렉터리는 삭제하지 않습니다. `--execute` 없이 공식 API를 호출하지 않습니다.
- 저장 실패·불확실한 응답은 자동으로 잠금을 지우거나 무료 재시도하지 않습니다. 원격 예약·원본·장부를 먼저 대조해야 합니다. 호출 전 실패가 확실하고 예약도 없을 때만 기존 정상본으로 잠금을 해제합니다.
- 실행 중 새 달의 작업을 추가하되 과거 월은 보존합니다. `--collect-month`를 생략하면 기존 수집기의 작업 우선순위에 따라 진행합니다. 이미 완료된 월의 정정 재조회는 별도 정책이 필요합니다.
- 이 명령은 비공개 수집 장부만 갱신합니다. 홈페이지 데이터 릴리스를 자동으로 덮어쓰지 않습니다.

### 2026-09-24 실제 종단 검증

최초 부분 복원 실행에서 2016년 11월 작업에 공식 API를 1회 호출해 정상 본문 49,403 bytes를 보존했습니다. 기존 호출 8,638회를 이관하고, 호출 장부는 8,639건·자료 있음 작업은 8,030개가 됐습니다. 새 정상 manifest는 `d0ef38765e56d0d884629bceda720819614518fbd4bd399848b3363940b93e37`입니다.

장부·지역 코드 2개 파일 21,637,291 bytes를 복원하는 데 읽은 객체의 **압축 해제 크기**는 25,065,772 bytes였습니다. 전체 원본 복원 크기 2,956,831,152 bytes와 비교하면 약 0.85%입니다. manifest·HTTP·압축 전송량을 포함한 네트워크 측정이나 웹 지도 성능 수치는 아닙니다. 새로 업로드하거나 변경한 파일은 4개, 16,780,398 bytes입니다.

별도 새 디렉터리에서 변경된 4개 파일을 원격으로 다시 복원해 해시를 검증했고, 기존 18,971개 경로 보존·장부 무결성·17,907개 참조·9,275개 스냅샷을 확인했습니다. 원격 예약은 저장 완료, 실행 소유권은 해제됐습니다. 이 후속 검증은 공식 API를 호출하지 않았습니다. 전체 과거 원본의 바이트별 재검증은 이전 전체 복원 기록과 구분합니다.

이어 다른 새 실행 디렉터리에서 재시작해 1회를 추가 호출했습니다. 기존 호출 이관은 `already_imported: true`로 건너뛰어 중복 합산하지 않았고, 원격 최신 장부는 호출 8,640건·자료 있음 8,031개·정상 빈 응답 286개·실패 1개·대기 53,634개가 됐습니다. 이 두 번째 manifest는 `c10fb63120b0a76bd8139ec1f5a903d0d88f28194371703f987eb776ee22c4be`이며, 2016년 11월 전체 수집 완료를 뜻하지 않습니다.

**정기 실행 전 저장 효율 관문:** 실제 DB 파일 점유는 두 실행 전 560,193,536 bytes에서 572,678,144 bytes로 늘었습니다. 현재 새 정상본마다 장부 전체와 manifest 전체를 별도 불변 객체로 저장하므로, 1회 호출씩 실행하는 방식의 저장 증가율을 운영에 그대로 적용해서는 안 됩니다. 필요한 원본만 복원하는 개선과 메타데이터 버전 저장 효율은 별도 문제입니다. 정기 실행을 활성화하기 전에 장부·manifest의 증분 보존 또는 검증된 버전 보존 정책을 설계하고 10년 수집 예상 용량을 재산정해야 합니다. 기존 버전은 이번 작업에서 삭제하지 않았습니다.

## 2026-09-24 저장 형식 v2와 실제 재시작 검증

위 전체 재저장 방식은 v1 당시 결과입니다. 원격 실행기는 이제 `real_estate_manifest`의 v2를 사용합니다. 전체 복원과 수동 백업은 v1·v2 입력을 모두 읽습니다. **v2를 읽지 못하는 과거 소스로 원격 실행기를 되돌리면 안 됩니다.** 웹 공개 릴리스와 비공개 백업 형식은 별개입니다.

- 장부를 64KiB 조각으로 나누고 바뀐 조각만 하나의 새 객체에 모아 저장합니다. 나머지 조각은 기존 불변 객체의 위치·크기·해시를 그대로 참조합니다. 여러 번 갱신해도 조각이 다른 복원 조립법을 참조하지 않으므로 과거 버전들을 순서대로 적용할 필요가 없습니다.
- 파일 목록은 경로 해시에 따른 고정 64묶음입니다. 변경된 묶음과 작은 최상위 색인만 추가 저장합니다. 각 묶음·조각·파일의 크기와 해시, 목록 개수·중복·경로·버킷 소속을 검증합니다.
- 새 객체는 원격에서 다시 읽어 해시를 확인한 뒤 정상본 포인터를 바꿉니다. 중간 실패는 이전 정상본을 유지하며, 공식 API를 호출한 실행의 소유권은 복구 검토 없이 해제하지 않습니다.
- 이전 목록·장부·원본은 삭제하지 않습니다. 새 버전은 부모 목록 자체를 불러오지 않고 복원되지만 공유하는 과거 데이터 객체는 여전히 필요합니다.
- 수동 전체 `backup`은 호환용 v1을 생성합니다. 이 경로는 전체 참조 검증과 장부 전체 저장을 하므로 빈번한 정기 수집에는 부분 복원 실행기를 사용합니다.

실제 D1에서 각각 새로운 실행 폴더로 공식 API를 1회씩 호출했습니다. 새 수집 우선순위를 따라 인천 `28125`의 2025-07 전월세·매매 작업을 이어받았고, 기존 호출 예산은 재이관하지 않았습니다.

| 항목 | v2 최초 전환 | v2 재시작 |
|---|---:|---:|
| 새 공식 API 호출 | 1 | 1 |
| 바뀐 장부 조각 원본 크기 | 405,504 bytes | 393,216 bytes |
| 새로 쓴 목록 묶음 | 64 | 4 |
| 최상위 manifest | 6,216 bytes | 6,213 bytes |
| 5개 DB 실제 점유 증가 | 2,428,928 bytes | 323,584 bytes |
| 확정 호출 장부 | 8,641 | 8,642 |

최초 전환은 64개 목록 묶음을 한 번 새로 저장하는 비용이 포함됩니다. DB 증가량은 원본·정규화 결과·장부·목록·예약을 포함한 실제 점유입니다. 조회한 거래 내용이 다르므로 이전 v1의 2회 실행 증가량 12,484,608 bytes와의 비교를 일반적인 절감률이나 10년 용량 보장으로 해석하지 않습니다.

재시작 후 manifest는 `9fd675dda3597c98689f5cd6538d7dc17d8e01c48521f31654873dce159eafab`입니다. 별도의 새 폴더에서 원격 자료만으로 장부와 추가·변경 파일 7개를 복원했습니다. 이전 18,977개 경로와 불변 파일 참조가 유지됐고 SQLite 무결성, 호출 8,642건, 스냅샷 9,278개, 참조 17,913개가 일치했습니다. 이전 v1 장부도 다시 내려받아 무결성과 호출 8,640건을 확인했습니다. 새 검증은 공식 API를 호출하지 않았으며 변경되지 않은 과거 원본 전체의 재다운로드를 뜻하지 않습니다.

이 시점의 실제 작업은 자료 있음 8,033개·정상 빈 응답 286개·실패 1개·대기 53,632개입니다. 각 작업은 지역·계약월·거래유형 단위이며 건물이나 거래 건수가 아닙니다. 현행 지역 코드로 조회한 이력이고, 과거 유효 코드 대응표 검증은 별도로 남아 있습니다.

기존 데이터 보존과 저장 증가량 개선은 검증했지만 정기 실행은 아직 활성화하지 않았습니다. 자동 실행용 인증, 중단된 예약 복구, 전체 이력 용량 추정과 공개 자료 갱신·롤백 관문은 계속 적용합니다. [현재 확보 우선순위](PROPERTY_ACQUISITION_PRIORITY.md)를 따릅니다.
