# 거래 스냅샷 저장 압축 개선

기준일: 2026-09-28 KST. 신규 수집 스냅샷의 저장량을 줄이는 변경이며, 20년 수집 완료나 전체 무료 저장 용량 확보를 뜻하지 않습니다.

## 선택과 실측

기존 로컬 비공개 정규화 스냅샷 중 **파일 크기가 큰 40개**를 같은 정규 JSON 바이트로 풀어 비교했습니다. 전국 무작위 표본이 아니며, 계측 원문과 파일 경로는 공개하지 않습니다.

| 표현 | 합계 바이트 | 기존 gzip 대비 |
|---|---:|---:|
| 정규 JSON | 164,991,215 | 압축 전 |
| 기존 gzip level 6 | 14,363,639 | 기준 |
| gzip level 9 | 13,310,022 | 7.34% 감소 |
| XZ preset 3, CRC64 | 9,110,488 | **36.57% 감소** |

XZ 압축에 걸린 시간은 이 표본 합계 약 5.40초였습니다. 이는 압축 함수의 로컬 실행 시간이며 네트워크·전체 수집 시간 개선 비율이 아닙니다. 작은 스냅샷은 XZ 헤더 때문에 gzip보다 커질 수 있습니다. 표의 바이트는 D1의 최종 SQLite 페이지·인덱스 사용량도 아닙니다.

기존 운영 실행 한 번의 저장 분해에서는 신규 base64 payload 약 14.77MB 중 스냅샷이 8.83MB, 원본 XML이 2.81MB, manifest가 2.20MB, 체크포인트 등이 나머지를 차지했습니다. 이미 gzip인 스냅샷을 다시 zlib으로 압축해도 거의 줄지 않았습니다. 따라서 원본·출처 필드를 제거하지 않고 **새 스냅샷을 만들 때** 더 넓은 중복 범위를 압축하는 XZ를 선택했습니다.

## 호환성과 보존

- 새 스냅샷만 `.json.xz`, `encoding: xz`로 저장합니다. 기존 JSON·gzip 파일, 원본 XML, 체크포인트와 이력은 재작성하거나 삭제하지 않습니다.
- 저장 바이트의 SHA와 복원한 정규 JSON 바이트의 SHA를 각각 확인합니다. 거래 값·행 ID·출처·중복 발생 횟수와 공개 JSON 계약은 바뀌지 않습니다.
- 현행 decoder는 기존 무압축 JSON, gzip 및 신규 XZ를 읽습니다. gzip의 과거 헤더와 시간 필드는 저장된 바이트 그대로 유지됩니다.
- archive manifest/객체 계약과 broker SQL 계약은 그대로입니다. 허용 파일 확장자에 `.json.xz`만 추가합니다.
- 선택적 원격 hydration → 업로드 → manifest → 전체 복원 → 원문 재정규화 대조 → 공개 후보 생성까지 JSON/gzip 부모와 신규 XZ가 섞인 테스트를 둡니다.
- XZ 지원 이전 코드로 새 체크포인트를 읽는 **전방 호환은 제공하지 않습니다**. 수집기 코드를 롤백하더라도 XZ decoder는 유지해야 합니다. 과거 head는 별도 디렉터리로 읽기 전용 복원할 수 있지만, 자동으로 현재 head를 되감거나 이후 확보 자료를 버리지 않습니다. 기존 공개 정적 릴리스에는 영향이 없습니다.

## 실패 방어

복원 크기는 기존 128MiB 이하로 제한하고, XZ decoder의 사전 메모리 한도를 64MiB로 제한합니다. 주장한 복원 크기보다 1바이트까지만 읽어 과대 팽창을 탐지하며, 잘린 스트림·CRC 오류·연결된 두 번째 스트림·후행 가비지·해시 불일치·확장자와 encoding 불일치를 거부합니다. 실패한 복원을 성공본으로 게시하지 않습니다.

100회/64MiB 원천 호출 예산, `raw_budget_preflight`, shard 상한, lease 및 head CAS, 불확실한 쓰기 자동 재시도 금지는 변경하지 않습니다. raw preflight는 여전히 **원본 payload만** 검사하며 최종 manifest·스냅샷·체크포인트를 모두 담을 공간을 보증하지 않습니다.

## 남아 있는 수집 병목

직전 성공한 범위 전환 실행은 100회 호출로 86개 지역·유형·월 작업을 처음 확보했습니다. 112개 지역의 241개월 장부 53,984개 중 5,824개는 원천 제공 전이며, 가용 48,160개 중 4,011개만 확보된 상태였습니다. 미확보 가용 작업은 44,149개입니다. 실패를 거래 0건으로 계산하지 않습니다.

같은 효율이 유지된다고 가정해도 1일 6회 전부 backfill이면 약 86일, 실제처럼 4번 중 3번을 backfill에 쓰면 약 114일입니다. 이는 API 오류·월별 자료량·페이지 수·새 달·저장 중단을 제외한 단순 처리량 추산이며 완료일 약속이 아닙니다. 근본적인 저장 공간 확보 없이 요청 수만 늘리지 않습니다.
